# 25. Zi Guided Setup Is a Planner First, With the Interface and Its Language Deferred to a Trigger

- **Status:** PROPOSED
- **Date:** 2026-09-18
- **Deciders:** TBD
- **Supersedes:** None
- **Superseded by:** None

## Context

A product proposal for "Zi Setup", a device-aware visual installer and shell configurator, was evaluated on 2026-09-18. Its core idea is sound: separate installing Zi from changing how a shell behaves, translate a small set of user choices into ordinary readable Zsh, show the resulting diff before applying it, and never make normal shell startup depend on the tool. Its delivery shape is a standalone Go application with a terminal interface, a recipe catalog, three presentation modes, and existing-configuration patching, provisionally in a new repository.

The current installer is `z-shell/src` `public/sh/install.sh`, a POSIX `sh` script fetched with `curl | sh`. It takes `-i`, `-a`, and `-b` flags, appends fixed blocks to `.zshrc`, and reuses `z-a-meta-plugins` bundles (`@annexes`, `@zunit`) for the only capability sets it offers. Three defects in its update and integration paths were filed the same day ([z-shell/src#203](https://github.com/z-shell/src/issues/203), [#204](https://github.com/z-shell/src/issues/204), [#205](https://github.com/z-shell/src/issues/205)) and are independent of any new tool. The Zi loader (`public/zsh/init.zsh`, sourced from `.zshrc` as a `startup-file`) is the runtime seam and was hardened in `src` pull requests 197 and 201. The only console in the organization, `z-shell/zi-console`, is a 2021 `zsh/zcurses` and ZUI plugin last pushed in February 2022.

Organization constraints that the proposal did not see:

- Policy is Zsh-first ([AGENTS.md](../AGENTS.md)). `zsh-lint` is the single Go precedent and is a versioned tool under [ADR-0007](0007-release-publication-flow.md) class 2, which [ADR-0009](0009-testing-ci-strategy.md) binds to a tag-time test gate and SAST. A compiled setup tool would join that class and additionally need platform artifacts, checksums, and a bootstrap that downloads an executable, none of which the `curl | sh` path does today.
- A Zsh-native interface would ship through `zi` itself at no distribution cost, but `zsh/zcurses` is a separately built module and at least one current Zsh 5.9.2 distribution build ships without it, so it cannot be assumed at the 5.8.1 floor.
- `z-a-meta-plugins` already is the capability-bundle concept ([ADR-0002](0002-zi-as-canonical-plugin-manager.md) names `zi` canonical). A second recipe catalog would be a competing source of truth.
- The organization has one maintainer. A planner, a recipe schema, three presentation modes, patch export, platform builds, and terminal testing is a product, not a feature.

## Decision

1. **Boundary.** Guided setup installs Zi and generates ordinary Zsh; it does not manage a running shell and it never becomes a startup dependency. The configuration home is resolved by one rule in both the planner and the startup block: `$XDG_CONFIG_HOME/zi` when `XDG_CONFIG_HOME` is set and absolute, otherwise `$HOME/.config/zi`. Under it the plan has three targets: `init.zsh`, the loader asset the installer already places there, written from the copy bundled with the installer or fetched at a commit-pinned URL and verified against the checksum `src` publishes in `public/checksum.txt` before its bytes enter the plan, then hashed like any other target; `setup/pre.zsh` for settings that must exist before `init.zsh` is sourced, such as `ZI[LOADER_HISTORY]`; and `setup/shell.zsh` for everything that runs after `zzinit`, such as plugin recipes. Guided setup always installs the loader profile (today's `-a loader` output); the direct profile that sources `zi.zsh` is not a guided-setup output. The plan always includes the integration block in `${ZDOTDIR:-$HOME}/.zshrc`, the same dotfile resolution the installer uses today; the block keeps the absolute `XDG_CONFIG_HOME` check, declares `typeset -gA ZI`, then runs `source setup/pre.zsh && source init.zsh && zzinit` as one guarded chain, sources `setup/shell.zsh` only when the whole chain succeeded, and otherwise prints one diagnostic naming the step that failed. The loader does not discover fragments and is not changed by this decision. Normal startup must not execute the setup tool, parse its state, or load its libraries. Shell-behaviour choices (history, editing mode, completion) are separate, visible choices with `keep current` as the default for existing users.
2. **Planner first, in `src`.** The first deliverable is a headless `plan` and `apply` pair beside `install.sh`, in the installer's own dialect (POSIX `sh`, with Zsh only where the plan is evaluated by Zsh), tested in `tests/installers.sh`. `plan` records, for every target, the expected current content hash and the exact new content, and prints the unified diff. `apply` re-validates every target against the recorded hash before writing anything, aborts on the first mismatch without writing, and writes a receipt listing what changed. `.zshrc` is never replaced whole: the planner owns one marker-delimited managed block, replaces it idempotently, and preserves every byte outside it; when the block's current content differs from the receipt's hash, `apply` refuses, prints the intended block and a patch, and leaves the file untouched, which is the supported workflow for externally managed dotfiles. `plan` also recognises the exact blocks today's installer writes, the direct `zi.zsh` block and the loader block, and migrates a byte-identical one into the managed block as a visible part of the diff, carrying its installation-time `ZI_HOME`, `ZI_BIN_DIR_NAME`, and ref into `setup/pre.zsh` as `ZI[HOME_DIR]`, `ZI[BIN_DIR]`, and `ZI[STREAM]`, and refusing when those values cannot be mapped; a recognised block that was edited, or any other Zi integration, is reported and left alone, and `apply` refuses rather than initialise Zi twice. Delegated flows never start an interactive shell and never source the user's dotfiles: recipe installation is deferred to the first shell start and the receipt says so, which is the src#204 fix, covered in `tests/installers.sh` with a `zsh` double. The `-b` ref is one plan input used by both the checkout phase and the hashed `init.zsh` content (`ZI[STREAM]`); it must match a conservative grammar (ASCII letters, digits, `.`, `_`, `/`, `-`, no leading `-`, no `..`) and is written into Zsh only through single-quoted serialization. `apply` consumes only the plan artifact it is given, identified by its content hash, and never recomputes or refetches content; it takes a lock on the configuration home, writes each target to a temporary file and renames it into place, and records the installed hash of every target in the receipt; a missing or invalid receipt makes the next `plan` treat every target as unmanaged, so nothing that is not byte-identical to a known template is overwritten. Updating an existing Zi checkout is a separate plan phase, not a file target: it fetches and fast-forwards only, refuses with the checkout state when a fast-forward is impossible, and discards local state only behind an explicit opt-in flag that the plan shows. The `install.sh` flags that write configuration (`-i`, `-a loader`, `-a annex`, `-a zunit`) delegate to the same planner and apply implementation; the current append-only integration path is removed once the planner covers it, so no second configuration write path remains. The default invocation becomes the loader profile, and the direct `zi.zsh` profile is deprecated with a printed notice while its block stays recognised for migration. `-i skip` keeps its meaning: the plan has no `.zshrc` target and consists of the checkout phase and the configuration-home targets only, so install-only use continues to work. `-a zpmod` is exempt: it hands off to `install_zpmod.sh`, which downloads and compiles a module and produces no file content the plan contract can represent, so it keeps its own execution path and the planner never invokes it. The three filed installer defects are fixed on this path, not around it.
3. **Recipes come from meta-plugins.** A capability offered by guided setup is a `z-a-meta-plugins` label plus a configuration fragment authored in `src`. The planner does not read the meta-plugins catalog, which is Zsh evaluated at load time; it ships a small versioned data table in `src` that lists each offered label and the meta-plugins revision it was verified against, and a label absent from that table is a plan-time error. `setup/shell.zsh` loads the labels the way the installer already does, in one `zi light-mode for z-shell/z-a-meta-plugins @<label> ...` command, so meta-plugins is loaded before any label it defines, and pins meta-plugins to the table's verified revision with the `ver` ice, so an approved receipt cannot expand a label differently at first shell start; rerunning `plan` is how the pin advances. No separate catalog, schema, or marketplace is created; the gallery in the wiki remains the documentation.
4. **Interface on a trigger.** A terminal interface is built only after the planner has shipped and the maintainer records, on an issue, that the interface is now the bottleneck for adoption. Until then, sketches and previews are not implemented.
5. **Language and home decided with the trigger, with a default.** If the interface is built, it is a separate repository named `zi-setup`, class 2 under ADR-0007, written in Go, unless by then `zsh/zcurses` availability has been verified on every supported platform at the repository floor, in which case a Zsh-native interface shipped through `zi` is preferred. Under [ADR-0017](0017-licensing-standard-by-provenance.md) a compiled tool that is not loaded into the user's shell is GPL-3. The fragments are authored in `src` and reference `z-a-meta-plugins` by label only, never by copied content, so that repository's GPL-3 L2 status is untouched; the classification of the generated file is settled under ADR-0017 when the recipe contract lands, not here.
6. **Non-goals.** Arbitrary `.zshrc` migration, removal of other plugin managers, system package installation, font installation, `chsh`, and live management of the running shell are out of scope for every stage of this decision.

## Consequences

### Positive

- The valuable part of the proposal, a reviewable plan that produces readable Zsh, ships first and cheaply, inside the repository and test harness that already own installation.
- No new language, repository class, release pipeline, or catalog is created on the strength of a design sketch.
- The interface question is answered by evidence from the shipped planner instead of in advance.

### Costs and risks

- A headless planner is less visible than a terminal interface; the proposal's distinctiveness argument is deferred with it.
- Keeping the planner in POSIX `sh` limits the richness of the plan format; a JSON receipt needs a careful writer in that dialect or a Zsh helper.
- If the trigger fires quickly, some planner code may be reimplemented in the interface's language. To bound that cost, a future interface invokes the `src` command line (`plan`, `apply`) and presents its output; it does not parse the plan or receipt files, which are human-readable and carry no compatibility promise until a versioned interchange format is decided separately.

## Alternatives considered

1. **Build the full Go application now, as proposed.** Rejected for now: it creates a class 2 repository, a release pipeline, and a bootstrap download before any user has seen a plan, and it duplicates meta-plugins as a catalog.
2. **Build a Zsh-native interface now on `zi-console`.** Rejected: `zsh/zcurses` availability is unverified at the floor and the console has been dormant since 2022; reviving it is its own decision.
3. **Extend `install.sh` with more flags and presets only.** Rejected: it keeps the append-only integration that the filed defects show is not idempotent, and it never produces a reviewable plan.
4. **Do nothing.** Rejected: the boundary between installing Zi and changing shell behaviour is worth recording even if no tool is built, because the installer already crosses it.
